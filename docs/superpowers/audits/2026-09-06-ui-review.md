# UI review — workout-tracker

Senior product design pass, 2026-09-06. Read-only; no code changed.
Scope: `frontend/src/pages/*`, `frontend/src/components/*`, `index.css`, `lib/theme.js`,
the three prior design specs, and the six live screenshots.

---

## Verdict

**Adequate-to-good, and unusually well-reasoned for a hobby app — but the one screen that
matters most is the least designed.** Home, History, Progress and the reworked auth screens are
clean, consistent and honest; the comment density in this codebase shows real decisions being
made and recorded rather than styles being copy-pasted. The in-gym path is *nearly* excellent —
one tap per set, prefilled from a progressive-overload suggestion, auto rest timer, wake lock,
auto-advance — which is better than Strong or Hevy on the happy path. It falls down on the
things that only show up on the fifteenth set: the primary button walks down the screen as you
log, the next exercise scrolls under the fixed header, a mis-tap deletes a set with no confirm
and no undo, and a flaky gym wifi can wedge the button on "Logging…" indefinitely. For the
single current user this is a good app with four sharp edges. For the 3-4 users arriving soon,
the fixed 4-day plan with no way to add an exercise is the thing that breaks first.

## Top 5 issues, ranked by user impact

### 1. A bad gym connection wedges the primary button on "Logging…" forever

**What's wrong.** `req()` (`frontend/src/api.js:14-35`) calls `fetch` with no timeout and no
`AbortController`. `logSet` sets `logging = true` (`frontend/src/pages/Workout.jsx:280`) and only
clears it in the `finally`-equivalent at line 330, after the promise settles. On a gym wifi that
associates but doesn't route — the single most common gym network failure — iOS will sit on that
socket for 30-75 seconds before the fetch rejects.

**Why it matters in the gym.** For up to a minute the Log Set button reads "Logging…" and is
`disabled` (`Workout.jsx:529`). You cannot log the set you just did, you cannot log the next one,
and nothing tells you whether the set landed. Your rest timer never started, because
`setRestStartMs(Date.now())` is on line 307, after the await. The workout stops.

**Smallest fix.** Five lines in `api.js`: wrap the fetch in `AbortSignal.timeout(8000)` (or a
manual `AbortController` + `setTimeout`) and let the existing `catch` in `logSet` fire. Then fix
the copy at `Workout.jsx:329` — `'Failed to log set'` should say what to do:
`"Couldn't save that set — tap Log Set again"`. The typed weight/reps survive the failure
already, so retry genuinely is one tap; the message just doesn't say so.

### 2. The Log Set button walks down the card after every single set

**What's wrong.** Inside each expanded exercise card the order is: cues link → note →
last-workout block → **logged sets** (`Workout.jsx:511-513`) → **steppers + Log Set**
(`Workout.jsx:516-533`) → muscle chips. Every logged set inserts a ~35px `SetRow`
(`Workout.jsx:34-55`) *above* the controls.

**Why it matters in the gym.** By set 3 the stepper pair and the Log Set button sit ~105px
lower than where you tapped for set 1 — and lower still relative to the fixed `TimerBar`, which
occupies the bottom ~65px (`index.css:170-177`). You are re-acquiring the same target after every
set, one-handed, while breathing hard. Nothing else on this screen moves; only the thing you
touch most.

**Smallest fix.** Swap two JSX blocks: render `{exSets.map(...)}` *after* the logger `<div>`
instead of before it. The controls then sit at a fixed offset from the card header for the whole
exercise, and the set you just logged appears immediately below the button you just pressed —
still in view, still confirming. The set-dots in the card header (`Workout.jsx:457-463`) already
carry the at-a-glance progress, so nothing is lost by demoting the list.

### 3. Auto-advance scrolls the next exercise underneath the fixed header

**What's wrong.** On completing an exercise, `scrollIntoView({ block: 'start' })`
(`Workout.jsx:321-326`) aligns the next card to the top of the *viewport*. The header is
`position: fixed` (`App.jsx:41`) and measures ~47px. There is no `scroll-margin-top` anywhere in
the app.

**Why it matters in the gym.** The single moment auto-advance exists to serve — "which exercise
am I on now?" — ends with the new exercise's name and its `3×8-12` target hidden behind the
"🏋 Gym Tracker" bar. You have to scroll up to read what the app just decided for you, which
undoes the whole feature.

**Smallest fix.** One property on the `DisclosureRow` `style` prop already being passed at
`Workout.jsx:429`: `scrollMarginTop: 'calc(var(--header-height, 0px) + 8px)'`. `--header-height`
is already published on `.page-shell` by `App.jsx:47` and inherits down, so this needs no new
plumbing and stays correct if `ResumeBanner` ever changes the header's height.

### 4. Deleting a set is one unconfirmed, un-undoable tap, 16px from the numbers you read

**What's wrong.** `SetRow`'s delete button (`Workout.jsx:47-51`) is a 44×44 `×` that fires
`deleteSet` immediately. It sits in a `gap: 16` flex row (`Workout.jsx:43`) right beside the
`60kg × 8` text you look at after every set. Meanwhile the app's *two other* delete actions —
sessions (`History.jsx:97-102`) and personal bests (`PersonalBests.jsx:57-68`) — both use a
tap-again-to-confirm pattern with a 3s timeout, and `ResumeBanner.jsx:37-48` uses an explicit
✓/✗ confirm. The one destructive action performed mid-workout, with sweaty hands, is the only one
with no guard.

**Why it matters in the gym.** There is no undo and no local cache: the set is gone from the
server. You will re-log it from memory, or not notice until the History screen.

**Smallest fix.** Reuse the pattern that already exists twice: lift a `confirmSetId` state into
`Workout`, pass `armed` into `SetRow`, render `×` → `✓?` on first tap with the same
`setTimeout(..., 3000)` reset. About 8 lines, no new concepts, and it makes the app internally
consistent at the same time.

### 5. Progress is a wall of 12 identical chips over an empty screen — and their tap targets overlap

**What's wrong.** Two defects compounding.
(a) `Progress.jsx:26` initialises `selected = null` and `Progress.jsx:30` fetches only the
exercise list, so the screen renders the chip cloud and nothing else until you tap. The
screenshot shows ~600px of empty page below the chips.
(b) The chips are `Chip` with `onClick`, which adds `className="tap-target"`
(`Chip.jsx:33`). `.tap-target::after` (`index.css:131-135`) paints a `max(100%, 44px)` invisible
hit area centred on a chip that is only ~27px tall (0.8rem text + `5px 14px` padding + 1px
borders). The row `gap` is 8 (`Progress.jsx:60`), so **horizontally adjacent chips' hit areas
overlap by ~14px and vertically adjacent rows overlap too**. Tapping near a chip edge charts the
wrong exercise.

**Why it matters.** Progress is the second most-visited screen and the payoff for logging at all.
Today it shows a chooser with 12 equal-weight options, no default, no ordering by relevance
(`ALL_EXERCISES` is alphabetical), and a mis-tap rate at the edges.

**Smallest fix.** (a) One line in the effect at `Progress.jsx:30`:
`.then(d => { setExercises(d); setSelected(s => s ?? d[0]?.exercise_id) })` — the screen then
opens on a real chart. (b) Give toggle chips a real box instead of a phantom one: in `Chip.jsx`,
when `onClick` is present add `minHeight: 44, display: 'inline-flex', alignItems: 'center'` and
drop the `tap-target` class for that branch. Raise `Progress.jsx:60`'s gap from 8 to 10.

## Everything else

### The in-gym path (the rest of it)

- **The happy path is genuinely 1 tap per set, and that's the app's best idea.** Workout opens
  with the first incomplete exercise expanded and prefilled (`Workout.jsx:224-230`), prefill
  carries the last logged set forward within the exercise, and `overloadSuggestion`
  (`lib/overload.js`) supplies the next load. Strong and Hevy also cost one tap per set but
  neither *tells you what to lift*. Do not trade this away.
- **The suggestion is the most decision-relevant sentence on the screen and is styled like a
  footnote.** `Workout.jsx:502-504` renders "Suggested **62.5kg** · Target 8-12" at
  `type.size.base` (0.75rem) in mint, below a list of last workout's sets. It should outrank the
  raw history above it. Smallest change: swap the two blocks and bump the suggestion to
  `type.size.lg`.
- **Finish Workout is at the very bottom of the page** (`Workout.jsx:546-549`), below all five
  cards. Every real training app keeps Finish persistently visible (top-right). Here, after your
  final set there is no auto-advance (no next incomplete exercise), so you're left mid-page and
  must scroll past every collapsed card. The page header at `Workout.jsx:409-417` is a
  `justify-content: space-between` flex row **with only one child** — a right-hand action slot
  that was clearly intended and never filled. Putting a compact Finish there is a ~6-line change.
  Do *not* put it in the `TimerBar` next to "Skip"; that is a mis-tap waiting to happen.
- **Adjusting rest silently rewrites your permanent default.** `onAddRest` (`Workout.jsx:398`)
  calls the setter from `useRestPreference`, which writes to `localStorage` on every call
  (`lib/useRestPreference.js:10-17`). Tapping "+30" once because this set was heavy changes the
  default rest for every future set of every future session, and nothing on screen shows the
  current target — only the countdown. Either make it session-local, or (smaller) render the
  target in the label: `REST · 90s`.
- **Reps prefill after a weight bump is optimistic.** `prefillFor` returns
  `reps: lastSets[0].reps` (`lib/workoutFlow.js:23`) even when the suggestion added +2.5kg — so
  it proposes the top of last cycle's rep range at a heavier load. One-line improvement: when
  `sug.hitTarget` is true, prefill `repsLow`.
- **No tap feedback on most controls.** `index.css:38` clears `-webkit-tap-highlight-color`
  globally; only `.btn-primary`, `.btn-secondary` and `.btn-icon` restore an `:active` state
  (`index.css:67, 73, 80`). The disclosure header you tap to open every exercise, the nav tabs,
  the chips, and every bare `.tap-target` button give none. One rule —
  `button:active { opacity: .7 }` near `index.css:54` — covers all of them.
- **Warm-up sets are indistinguishable from working sets.** Two warm-up sets on bench count
  toward `ex.sets`, fill the set-dots, and trigger auto-advance one working set early
  (`Workout.jsx:310-313`). Strong and Hevy both solve this with a set-type flag. I am *not*
  recommending you build that (see below) — but it's the reason the auto-advance will
  occasionally feel wrong, and worth knowing rather than debugging later.
- **No way to add an unplanned exercise, swap one, or log a lift outside the 4-day plan.**
  Correct and deliberate today: one user, one fixed program, and it keeps the whole app simple.
  This is the single thing that breaks when users 2-4 arrive with different programs. Flagging as
  a sequencing risk, not a fix.

### Information hierarchy, screen by screen

- **Home — good.** "Start the next workout" wins: `Start Lower B` is the widest, brightest,
  highest-contrast object on screen. Two weaknesses. (a) Inside the exercise preview card the
  orange `3×4-8` rep schemes (`Home.jsx:140`) carry more chroma than the white exercise names, so
  the eye lands on reference data instead of on the lift; making them `colors.muted` and leaving
  the day colour to the button would fix the inversion. (b) Below the fold the screen becomes a
  developer footer: recovery rings → a 3-line disclaimer → an empty-state card → "Export my data"
  → a `v <sha>` build stamp (`Home.jsx:184-199`). The version stamp is load-bearing for deploys
  (AGENTS.md's PWA-cache gotcha) so keep it, but "Export my data" doesn't belong on the primary
  screen ahead of any data existing.
- **Workout — the one screen whose hierarchy is unresolved.** An expanded card stacks six blocks
  of near-equal weight (cues link, note, last workout, suggestion, logged sets, logger). Fixes
  1-2 and the suggestion promotion above are the hierarchy fix; nothing structural is needed.
- **Progress — see issue 5.** Also: the `🏆 PBs` pill (`Progress.jsx:51-55`) is the only navigation
  on the screen and is styled as a quiet mint outline in the corner. Fine.
- **History — good, and slightly under-informative.** The collapsed row gives day, date,
  completed, duration. It gives no number you'd scan for — total sets or volume. Adding
  `· 18 sets` to `History.jsx:147-150` would make the list worth scrolling. Small.
- **PersonalBests — inverted.** A 5-field entry form occupies the entire first screen
  (`PersonalBests.jsx:88-122`) above the list it produces. This is a page you visit to *read*
  your PBs and rarely to write one. Move the form below the list, or collapse it behind a
  `+ Add` disclosure (you already have `DisclosureRow`).
- **Auth screens — the rework landed.** Comparing `login.jsx` before/after: the duplicated
  "Log in / LOG IN" in the top bar is gone, the nav no longer frames a single-action page, the
  fields now have borders and a real `:focus` ring (`index.css:95-106`), and `Back to workouts`
  gives an installed PWA a way out. This is a clear before/after win; no notes.

### Empty and edge states

- **First run is the weakest state in the app.** With zero sessions, Home shows: the Upper A plan
  and a Start button (correct), then **eight recovery rings all reading "Not trained yet" with
  empty tracks**, then the 3-line estimate disclaimer, then an `EmptyState` card, then an export
  link for nothing, then a build hash. `MuscleGroupPicker.jsx:108` only bails on
  `!groups?.length`, and `groupRecovery([])` always returns all `MUSCLE_GROUPS`, so the picker
  can never be empty. **Smallest fix:** extend that guard —
  `if (!groups?.length || groups.every(g => g.freshness === null)) return null`. Same one-line
  treatment for the export link (`Home.jsx:188`): render it only when `sessions.length > 0`.
- **Progress / History / PersonalBests empties are all fine** — `EmptyState` is used consistently
  and the copy is human ("Complete a workout to see progress here.").
- **"Log at least 2 sessions to see a trend"** (`Progress.jsx:83`) is exactly the right partial
  state. Keep.
- **`Unknown workout day.` is a whole screen made of a developer error string**
  (`Workout.jsx:274`) — red text on black with no way out. Rare, but it's a dead end with no
  navigation. Give it a sentence and a "Back to Home" button, or route to `/`.
- **The last-performance loading placeholder is a literal `…` paragraph** (`Workout.jsx:491`).
  You have a `Skeleton` component. One-line swap.

### Consistency

The design-token and component-extraction work clearly landed and mostly holds. What's actually
still inconsistent:

- **The type scale has a hole in the middle.** `theme.js:31-39` defines 0.65 / 0.7 / 0.75 / 0.8 /
  0.875, then jumps to 1.75 and 2rem. Everything in between is a local literal: **8 sites at
  `0.9rem`**, **4 at `1.1rem`**, 5 at `1rem`, plus one each of 0.95 / 1.2 / 1.25 / 1.3 / 1.35 /
  1.4 / 1.5. That means exercise names (`Workout.jsx:449`), session titles (`History.jsx:144`),
  the app name (`TopBar.jsx:57`) and the Log Set label (`Workout.jsx:530`) are all untokenised.
  **Smallest fix:** add exactly two tokens for the two duplicated values (`body: '0.9rem'`,
  `strong: '1.1rem'`) and sweep those 12 sites. Leave the one-off display sizes alone — the
  tokens spec's own tier-3 precedent covers them.
- **`space` tops out below the app's actual section rhythm.** `theme.js:48-57` ends at
  `xxxl: 24`, but section margins in the wild are 28 (×2) and 32 (×3), which are therefore always
  raw numbers. Raw numeric margins outnumber `space.*` usages roughly 61 to 27. Add one
  `section: 32` token and use it for the four page-header margins.
- **`StatPair.jsx` is the only component that ignores `theme.js` entirely** — `'#9ca3af'`,
  `'#fff'`, `'0.75rem'`, `700`, `'0.08em'` hardcoded at lines 4-8, and its label block is a
  byte-for-byte reimplementation of `Eyebrow`. This is the "stat pair" the component-extraction
  spec deliberately deferred; it's now 12 lines and 5 minutes. `<Eyebrow>` + tokens.
- **`Chip`'s `color` prop is a silent no-op for label chips.** `Chip.jsx:25-26` hardcodes
  `colors.muted` in the non-toggle branch, so `ExerciseDetails.jsx:36` and `Workout.jsx:538`
  passing `color={color}` / `color={colors.muted}` do nothing. Either honour it or delete the
  prop at both call sites; today it reads as intent that isn't happening.
- **Two "done" colours in the same header row.** `Workout.jsx:450` marks a completed exercise
  with a mint `✓` while the set-dots beside it (line 460) fill in the **day** colour. On Lower B
  that's a mint tick next to orange dots meaning the same thing.
- **`.card` still has 8 padding variants** (12, 16, 20, `14px 16px`, `16px 20px`,
  `20px 8px 12px 0`, `space.xl`, `space.xxxl`) — the open decision the tokens spec explicitly
  deferred (§7 item 8). It's the least urgent item here; if you resolve it, `padding: space.xl`
  as the default with `20` for hero cards covers 10 of the 14 sites.
- **The `Workout` page subtitle is the only one that differs.** `Workout.jsx:415` uses
  `colors.muted` / `type.size.md`; Home, Progress, History and PersonalBests all use
  `colors.muted2` / `type.size.lg`.
- **Dead Tailwind class with a visible consequence.** `ExerciseCuesModal.jsx:22` still carries
  `className="max-w-md mx-auto"` from before Tailwind was removed (2026-08-25). Those classes no
  longer exist, so the cues sheet is **full viewport width on desktop** while every other surface
  is a 448px column. Replace with `maxWidth: 'var(--content-max-width)', margin: '0 auto'`.
- **The top bar's page label duplicates the nav bar's active tab.** `TopBar.jsx:94` renders a mint
  `HOME` in the top-right while `NavBar` renders a mint `HOME` at the bottom of the same screen —
  visible in the Home and Progress screenshots. It only adds information on `/workout` and
  `/exercise`, which have no nav tab. Render it only for those two paths, or delete it.
- **Desktop nav is the one thing that does look broken.** `NavBar.jsx:25-37` spans the full
  viewport with `justify-content: space-around`, so at 1047px the three tabs sit ~350px apart
  under a 448px content column (see the Progress and History screenshots). `TopBar` already
  solves this by wrapping its contents in `.page-shell`. Three lines to do the same in `NavBar`.

### Accessibility

- **The most-used control in the app is a `div`.** `DisclosureRow.jsx:31-40` is a click handler on
  a plain `<div>`: not focusable, no `role`, no `aria-expanded`, no keyboard, no `:active`. It's
  the exercise card header on Workout and the session row on History. Making it a `<button>` with
  `aria-expanded={isOpen}` fixes both call sites at once and is the highest-value a11y change
  here. Same for Home's "Last session" card (`Home.jsx:173-174`).
- **Focus rings exist for 5 selectors and nothing else.** `index.css:82-84` and `104-115` cover
  `.btn-primary`, `.btn-secondary`, `.btn-icon`, `.field`, `.field-toggle`. Not covered: every
  `NavBar` tab, every `Chip`, every `MuscleChip`, every bare `.tap-target` button (back links,
  export, PBs, delete, note). **Smallest fix:** replace the three-selector rule with
  `button:focus-visible, a:focus-visible { outline: 2px solid var(--mint); outline-offset: 2px }`.
- **Contrast.** Measured against the actual backgrounds (WCAG 2.x):
  - `#4b5563` on `--bg` = **2.61:1** — used for the build stamp (`Home.jsx:39`) *and* for the
    recovery disclosure paragraph (`MuscleGroupPicker.jsx:156`). The one paragraph the recovery
    spec insists must always be visible is the least readable text in the app. Move it to
    `colors.muted2` at minimum.
  - `muted2 #6b7280` on `--bg` = **4.08:1**, on `--card` = **3.86:1** — just under AA for normal
    text, and it's the standard page-subtitle colour (0.875rem, not "large text"). Nudging the
    token about one step lighter (~`#7c8593`, ≈4.9:1) clears AA everywhere it's used in one edit,
    with no layout change.
  - Everything else is comfortable: `muted` 7.8:1, mint 12.9:1, amber 11.8:1, all four day colours
    7.4-12.9:1 on bg and as button fills with the dark `#0a0a12` label.
- **Tap targets.** The 44px floor holds for buttons, with two exceptions: the number input inside
  `NumControl` is 72×~40px (`Workout.jsx:124-125` — `padding: '8px 0'` + 20px text), and the
  Progress chips discussed in issue 5. The number field is also the *fast path* — type "60"
  instead of 16 stepper taps — so it being the smallest target on screen is backwards. `padding:
  '10px 0'` fixes it.
- **Labels.** `NumControl`'s inputs have no accessible name at all, and its buttons are labelled
  `"decrease"` / `"increase"` (`Workout.jsx:118, 126`) — so a screen reader hears "decrease,
  increase, decrease, increase" on one card with no idea which is weight and which is reps. Pass a
  `label` prop through and interpolate it. Relatedly `WeightFieldLabel` uses `Eyebrow` (a `<p>`),
  not a `<label>` tied to the input.
- **`PersonalBests.jsx:136` puts a raw database id in the accessible name**
  (`delete personal best 7`). Use the exercise name and weight.
- **Motion is handled well.** `prefers-reduced-motion` is respected in `index.css:205-208`,
  `TimerBar.jsx:36`, `ExerciseDetails.jsx:21` and the auto-advance scroll
  (`Workout.jsx:322-324`). No notes.

### Copy

Mostly written for a person, with a few developer leaks.

Good, keep as-is: "0 = bodyweight only"; "Tap again to confirm"; "Log at least 2 sessions to see
a trend"; "Historical PBs from before you started logging here"; "Your workouts are saved either
way — logging in keeps them under your own profile"; the whole recovery disclosure in
`MuscleGroupPicker.jsx:10-13`, which is the most honest sentence in any fitness app I've read;
`LOG A SET` as the pre-first-set timer state.

Fix:
- `"Failed to start — is the backend up?"` (`Home.jsx:96`) and `"Export failed — is the backend
  up?"` (`Home.jsx:192`) — "backend" is your word, not the user's. `"Couldn't reach the server —
  try again"` says the same thing and is also true when the phone is the problem.
- `"Failed to log set"` (`Workout.jsx:329`) — mid-workout, this must say whether to retry. See
  issue 1.
- `"Unknown workout day."` (`Workout.jsx:274`) — an exception message rendered as a screen.
- `"Done → Home"` (`Workout.jsx:269`) — the arrow is developer shorthand. Just "Done".
- `"…"` as a loading state (`Workout.jsx:491`).

### Research: what Strong / Hevy / Fitbod converged on, and where this app should and shouldn't follow

The three have converged on a fairly narrow set of conventions for logging:

1. **A per-set row table** — `SET | PREVIOUS | KG | REPS | ✓` — with last session's numbers
   inline on each row and a large checkmark that commits the set.
2. **Numeric entry as the primary input**, usually via a custom in-app keypad; increment buttons
   and plate math are secondary.
3. **Rest timer auto-starts on set completion**, with a persistent countdown, quick ±15/30s,
   skip, and a sound/vibration at zero.
4. **Set typing** — warm-up / working / drop / failure — so warm-ups don't pollute volume, PR
   detection or set counts.
5. **Add / swap / reorder exercises and build supersets mid-workout.**
6. **Finish as a persistent top-right action**, followed by a summary screen (duration, volume,
   PRs).
7. Optional **RPE/RIR** per set; **plate calculator**; per-exercise rest defaults.
8. Fitbod diverges from the other two by generating the session and leading with a per-muscle
   recovery visual.

**Where this app's divergence is a deliberate advantage:**

- **One stepper pair per exercise instead of a set-row grid.** This is the right call and I'd
  defend it. A 5-column grid of ~30px inputs is a desktop pattern that phones inherited; it costs
  precision you don't have mid-set. One large pair of ±44px controls and one full-width primary
  button is strictly better for the stated context. Cost you're accepting: no per-set edit (only
  delete), and no visual alignment of planned vs. done. Both acceptable.
- **Steppers over a keypad.** Correct for the gym — no keyboard covering the screen, no precision
  typing with wet hands. The hold-to-repeat at `Workout.jsx:60, 93-98` (with the deliberate
  suppress-click on release) is a genuinely good piece of engineering and closes the "16 taps to
  get to 60kg" gap the comment describes. The *accident* is that the type-a-number escape hatch
  is the smallest target on the screen (72×40px) — fix that and the divergence is unambiguously
  better than the convention.
- **A prescriptive "Suggested 62.5kg"** (`lib/overload.js` + `Workout.jsx:499-506`). None of the
  three tell you what to lift next from your own log; they show history and leave the arithmetic
  to you. This is the app's single best differentiator and it's currently styled at 0.75rem.
  Promote it.
- **Honest recovery bands, never a percentage** (`lib/recovery.js:66-73`, and the research doc
  behind it). Fitbod ships an opaque per-muscle percentage with no disclosed inputs. Three bands
  plus "this is estimated from your logs only" is the more defensible product. Do not
  "improve" this into a number.
- **Rest state that survives navigation** (`lib/restTimerStorage.js` + `Workout.jsx:173`) and a
  **wake lock** (`lib/useWakeLock.js`). Both match or beat the commercial apps.

**Where the divergence looks like an accident rather than a decision:**

- **Finish at the bottom of a scrolling page** rather than persistently available. All three put
  it top-right. There's even an empty slot waiting for it (`Workout.jsx:409-417`).
- **No set typing**, which is why warm-ups mis-count toward `ex.sets`. I'd *keep* the divergence
  (it's real complexity for a marginal gain) — but know that it's the cause, not a mystery.
- **No add-exercise / no plan editing.** Deliberate today for one user on one program; it becomes
  an accident the moment a second person with a different split logs in.
- **A global rest default that in-session adjustments silently overwrite.** All three keep
  in-session adjustment and the stored default separate.

## What I would NOT change

**Already right — leave alone:**

- `theme.js` as a JS module rather than CSS custom properties. The recharts argument in
  `docs/superpowers/specs/2026-08-23-design-tokens-design.md` §1 is correct and the
  `theme.test.js` drift assertion is the right guard.
- The 12-component vocabulary (`Eyebrow`, `Chip`, `EmptyState`, `DayAccent`, `DisclosureRow`,
  `Toast`, `Skeleton`, `StatPair`, `TimerBar`, …). This is the right *size* of design system for
  this app. It needs sharpening, not replacing.
- The day-colour system (`DAY_COLORS` + `DayAccent` + `DAY_COLOR_FALLBACK`). Four colours, one
  meaning, consistent across Home / Workout / History / ResumeBanner. It's the strongest piece of
  visual identity in the app.
- `user-select: none` / `-webkit-touch-callout: none` on `body` (`index.css:45-47`). It costs you
  copy-paste and buys you no accidental text selection during fast tapping. Correct trade for the
  gym.
- Every `prefers-reduced-motion` guard.
- The auth screens as reworked. Compared against the before shots, this is done.
- The `1.75rem` page title + `muted2 / 0.875rem` subtitle pattern, now consistent on four screens.
- The recovery ring's sequential single-hue ramp and its refusal to use red/amber/green.
- `EXTRA_BOTTOM_CLEARANCE_FOR_TIMER_BAR` (`Workout.jsx:60-80`) — a measured constant with its
  measurement written down. Do not "simplify" this away.

**Tempting improvements I'm explicitly rejecting as overengineering:**

- **A component library, CSS framework, design-system package, or CSS-in-JS runtime.** You already
  removed Tailwind on purpose. Inline styles + `theme.js` + ~200 lines of `index.css` is the
  correct architecture at this size, and it costs the Pi nothing.
- **A state manager.** Four small contexts/hooks (`session`, `activeSession`, `useToast`,
  `useRestPreference`) are doing the job. Redux/Zustand/TanStack Query would add a dependency and
  a mental model to save nothing.
- **Converting the logger to a Strong-style per-set grid.** See the research section — this would
  be a regression for the stated context.
- **An offline write queue / IndexedDB sync layer.** A real solution here is background sync,
  conflict handling and a "pending" UI state — days of work and a permanent maintenance cost. The
  8-line timeout + honest retry copy in issue 1 recovers most of the value.
- **Warm-up/drop set typing, RPE/RIR, plate calculator, supersets, exercise reordering.** Each is
  a real convention and each is wrong for one person on one fixed program.
- **A full type-scale rationalisation** across all 23 distinct sizes. Add the two tokens that
  cover the 12 duplicated sites and stop.
- **Re-theming for light mode.** Dark-only is a decision, the tokens are consistent, and nobody
  lifts in a bright room wanting a white screen.
- **Anything that gates the app behind login or adds a route guard** — that's #86, deliberately
  scheduled.
