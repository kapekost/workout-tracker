# Plan edit v1 (#177) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development or
> superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Issue:** #177 · **Builds on:** #222 (`POST /api/plan/update`) · **Spec:** `2026-09-27-ai-plan-updates-design.md` §5

**Goal:** a profile edits sets/reps and swaps an exercise in its own plan, and resets the whole
plan to `plan_seed.DEFAULT_PLAN`. Nobody else's plan moves.

**Out of scope (owner, 2026-10-12):** dynamic workouts, AI integration, reorder, add or remove a
day, skipping a day. The AI paste-back screen (#223) and export (#220) stay as filed.

## What is already true

- The plan is per profile: `plan_days` / `plan_exercises`, seeded by `_seed_plan_for_profile`
  (`backend/main.py:94`), read by `GET /api/plan` (`main.py:987`) and the frontend `PlanProvider`.
- There is no plan write endpoint. #222 is that endpoint and is unbuilt.
- `sets`, `personal_bests` and `exercise_notes` key on `exercise_id` as free text with no FK to
  `plan_exercises`. Removing or swapping an exercise leaves its history in place.
- `plan_exercises.plan_day_id` cascades from `plan_days`, and `plan_days` cascades from `profiles`.
- The plan tables are in the export and in restore already; no migration is needed.

## Why #222 is `blocked`, and what unblocks it

#222 lists three blockers: #218 and #219 (both closed) and #220 (open, `ready`, `blocked`). #220 is
itself `blocked` only by #218/#219, so its label is stale. The remaining link is soft: the spec asks
for the export schema to be final so the update envelope answers it. The endpoint reads and writes
only `plan_days` / `plan_exercises`, which exist, and takes no input from `GET /api/plan/export`.
So #222 can be built now. Unblocking it is removing the `blocked` label from #222 (and #220), a
label edit for the implementer to do with the first PR. #221 and #223 stay blocked on #220/#222.

## Decisions

1. **One write path.** The editor calls `POST /api/plan/update` with the spec's envelope, as the
   issue asked, so the AI route later adds a caller, not a second validator. A manual edit sends
   `summary: "Edited in the app"` and `confirm: true` straight away: the user already saw what they
   changed, so no preview screen. The server still validates the whole payload first.
2. **Edit sets/reps** is a `modify` op with `sets`, `reps_low`, `reps_high`. Bounds are the spec's
   (sets 1 to 10, reps 1 to 50, high at least low).
3. **Swap needs a candidate list, which does not exist yet.** `modify` cannot change `exercise_id`,
   and `add` rejects an id already in the plan, so a swap is `remove` plus `add` in one envelope
   (all or nothing). But the default plan already holds every known exercise, so there is nothing to
   swap in. v1 adds a small `plan_seed.EXERCISE_CATALOG`: the `DEFAULT_PLAN` exercises plus a short
   list of alternatives per muscle group, each with name, muscles, cues and `yt_url` in the same
   shape. The swap sheet lists catalog entries not already in the plan, ranked by overlapping
   `muscles`. **Owner question below.**
4. **Swapping detaches history on purpose.** A swapped-in exercise has a new `exercise_id`, so the
   old lift's sets and PBs stay under the old id and Progress will show them only where it reads
   history by id. The sheet says so in one line before the swap is confirmed. Same-name renames are
   not offered, because `modify` of `name` under one id would merge two different lifts' history.
5. **Reset to recommended** is a new `POST /api/plan/reset`, own profile only, no body. In one
   transaction: delete the profile's `plan_days` rows (the cascade takes `plan_exercises`), then
   `_seed_plan_for_profile`. History tables are not touched. It is not a "destructive operation" in
   the GUARDRAILS sense (no schema, no agent deletion, user-initiated, own data) but it does discard
   the profile's edits, so the UI asks once before it runs. Resetting an unedited plan is a no-op in
   effect.
6. **Open workout.** If the profile has an uncompleted session, edits and reset answer `409` with
   "Finish or discard your current workout first". The open session was started from the old plan
   and its screen reads the plan live, so changing it underneath would move the exercise list during
   a set. The plan screen shows the same sentence instead of the edit controls.
7. **Concurrency.** Both endpoints take `BEGIN IMMEDIATE` before reading, like `create_session`.
8. **Frontend refresh.** After a successful write the page calls the `PlanProvider` `retry()` (it
   refetches `GET /api/plan`), so every screen sees the new plan. No new store.
9. **Where it lives.** A "Plan" page reached from Home (a link, not a new tab), one
   `DisclosureRow` per day, an Edit button per exercise opening a sheet with sets and reps steppers
   and a Swap action, and "Reset to recommended" at the foot. Existing tokens and components only.
   Export / paste-back (#223) will later sit on the same page.

## Split (GUARDRAILS: sized M or smaller each)

Order matters; each merges before the next starts. All three need the unblocking label edit first.

- **A. `POST /api/plan/update`, effort:M.** Backend only (this is #222).
  - Pydantic models from spec §5.1, op semantics §5.2, preview/confirm §5.4, `409` on an open
    session, `BEGIN IMMEDIATE`.
  - Tests that fail without it: *out-of-range sets / reps, `reps_high < reps_low`, unknown
    `day_key`, modify or remove of a missing id, add of an existing id each answer 400 naming the
    field*; *`confirm: false` writes nothing and the preview counts are right*; *`confirm: true`
    writes what the preview said*; *a failure on the second of two day updates leaves the plan
    unchanged*; *remove leaves `sets`, `personal_bests` and `exercise_notes` untouched*; *one
    profile's update never changes another's plan*; *409 with an open session*; *401 without a
    session*.
  - `Changelog: none`. Auth-adjacent (a new write route behind the session gate, no schema or token
    change): `staff-engineer-reviewer` before merge. Not deployed alone.
- **B. `POST /api/plan/reset` and `EXERCISE_CATALOG`, effort:M.**
  - Reset endpoint per decision 5; catalog constant in `plan_seed.py` plus `GET /api/plan/catalog`
    (read-only, session required) so the client does not carry a second copy of exercise content.
  - Tests: *reset restores `DEFAULT_PLAN` after edits*; *reset leaves sets, PBs and notes*; *reset
    does not touch another profile*; *409 with an open session*; *the catalog loads, ids are unique
    and none collides with `DEFAULT_PLAN` ids except by being the same exercise*.
  - Catalog content (cues, muscles) is training-science text: `workout-science` agent reviews it
    against the recovery research §7 limits; no recovery percentages, no "readiness".
  - `Changelog: none`.
- **C. Plan page, effort:M.** Frontend only.
  - Route, Home link, per-day rows, edit sheet, swap sheet with the history note, reset with one
    confirm, the open-workout message, refetch after write.
  - Tests: *saving sets/reps posts the modify envelope with `confirm: true` and refetches*; *swap
    posts remove plus add in one envelope*; *a 400 shows the field message, not a generic one*; *a
    409 shows the finish-first message*; *reset asks before posting*; *no edit controls render
    while a session is open*.
  - One entry in `frontend/src/lib/changelog.json`. Browser check at phone width: edit, swap,
    reset, and the open-workout case. A deploy of A + B + C together is a behaviour deploy
    (no schema change, so no export snapshot is required; a backup is still good practice).

## Risks to watch

- The `409` rule makes the editor unavailable mid-workout. If the owner would rather allow edits
  that apply from the next session, that needs a snapshot of the plan on the session; not in v1.
- `EXERCISE_CATALOG` is new authored content in a public repo; keep `yt_url` to links already used
  in the seed.
- Removing an exercise that has a PB makes the PB page list a lift the plan no longer offers.
  `PersonalBests.jsx` reads the plan today; part C checks it still renders PBs for ids missing from
  the plan and falls back to the stored id if not.

## Owner questions

1. **Swap candidates (decision 3):** is a fixed server-side catalog of alternatives right for v1,
   or would you rather swap only among the exercises already in the default plan (then a swap is a
   re-order across days and there is nothing new to author)? Recommendation: the catalog.
2. **Edits mid-workout (decision 6):** block them with a message (recommended), or allow them and
   apply from the next session?
